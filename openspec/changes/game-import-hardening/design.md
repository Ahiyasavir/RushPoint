# Design — game-import-hardening

## Context

`parseGameFile(input)` in `packages/shared/src/gameFile.ts` is the single trust boundary for an
imported game. It is pure (no Firebase), it is run **twice** — once client-side by the Builder as a
pre-check and once server-side by `importGameFile` — and its documented contract is that it *never
throws* and *never returns a partial game*.

The callable is already correct in the ways that matter for ownership:

| Threat | Status before this change |
|---|---|
| Identity smuggling (`ownerUid`, `id`) | **Closed** — excluded from `EXPORTED_GAME_KEYS`, assigned from `requireAuth(context)` after the parse |
| Publish-state smuggling (`visibility`) | **Closed** — excluded; forced to `'private'`; only `publishGame` may change it |
| Popularity/ranking smuggling (`playCount`) | **Closed** — excluded; forced to `0` |
| Wallet/credit fields | **Closed** — not on `Game`; not in the key set; nothing in the import path touches `wallets/` |
| Run ids / run state | **Closed** — runs are a subcollection; the import writes exactly one game document |
| Trash tombstone (`deletedAt`/`deletedBy`) | **Closed** — excluded |
| Owner secret (`integrationWebhookUrl`) | **Closed** — excluded |
| Unknown/extra fields | **Closed** — allow-list `pick()` at game/stage/task/`smart` |
| Envelope: format, version, 2 MiB bytes | **Closed** |
| Counts: 100 stages / 1000 tasks / 20 000-char strings | **Closed** |
| Top-level array / `null` / number / missing `game` | **Closed** — `isBag` gate, verified |
| Coordinates out of range | **Closed** — `isValidCoord` |

So this change is deliberately narrow. It adds nothing to the callable and nothing to the exported
document; it only closes the gaps *below* the four allow-listed levels.

## Demonstrated gaps (verbatim probe output against the shipped code)

Run with `npx tsx` importing `packages/shared/src/gameFile` directly (probe deleted after use):

```
A1 media.__proto__        ACCEPTED {"id":"t1",…,"media":{"kind":"image","url":"https://x/y.png","__proto__":{"polluted":true}}}
A2 steps[0].__proto__     ACCEPTED {"id":"t1",…,"steps":[{"title":"a","answer":"b","constructor":{"x":1},"__proto__":{"y":2}}]}
A3 game.branding.__proto__ ACCEPTED {"title":"G","stages":[],"branding":{"__proto__":{"p":1},"prototype":{"q":2}}}
B1 numericAnswer 1e999    ACCEPTED  → value= null typeof= object
B2 geofenceRadius -1e999  ACCEPTED  → geofenceRadiusMeters: null
B3 hintPenalty NaN        ACCEPTED  → hintPenalty: null
B4 stage.requiredTaskCount Infinity ACCEPTED
C1 answers = 5            ACCEPTED  → then: TypeError task.answers.some is not a function
C2 steps = "x"            ACCEPTED
C3 media = [1,2,3]        ACCEPTED
C4 description = 42       ACCEPTED
D1 answers x 200000       ACCEPTED
D2 steps x 50000          ACCEPTED
E1 deep text              THREW RangeError : Maximum call stack size exceeded
T top array / null / undefined / number → "This is not a RushPoint game file."  (already correct)
T game: []                → "The file contains no game."                        (already correct)
```

C1 is the sharpest: the crash happens in `gameStructureProblems → taskCompletabilityError`, which
`importGameFile` calls *after* `parseGameFile` returns clean, so the creator receives an opaque
`internal` (HTTP 500) instead of a field-level refusal.

E1 breaks the "never throws" contract. Note that the *object* input path happens to be safe today by
accident: `JSON.stringify` for the byte cap blows the stack first and the `try/catch` around it
reports "not valid JSON". Depending on which of two recursive functions overflows first is not a
defence; the explicit depth cap replaces it with a named refusal.

## Decisions

**D1 — One iterative pre-scan, before the clone.** A single `scanCandidateGraph(rawGame)` walks the
raw game with an explicit stack (no recursion → a hostile depth can never overflow the JS stack,
which is what E1 exploits) and returns a list of path-qualified errors. It runs *before* `clone()`,
because `clone()` is `JSON.parse(JSON.stringify(...))` and that is exactly what erases the evidence:
`Infinity`/`NaN` become `null` (B1–B4). It replaces the existing recursive `overlongString` helper,
which becomes a special case of the same walk (the existing over-long-string message and its test are
preserved verbatim).

**D2 — Prototype-pollution key names are REJECTED, not stripped.** `__proto__`, `constructor` and
`prototype` are refused wherever they appear as an object key. Rationale: the repo's participant
sanitizer strips because it must always produce *some* payload for a live participant; the importer
has the opposite duty — this module's stated rule is "REFUSE, NEVER GUESS", and a legitimate
RushPoint export can never contain such a key, so its presence means the document was tampered with
or generated by something else. Stripping would silently import a document nobody can vouch for.
This is also why the scan runs over the **whole** raw game, including keys the allow-list would drop:
a file carrying `__proto__` is not a file we quietly salvage.

**D3 — Unknown *fields* keep the existing strip policy.** Unrelated to D2 and unchanged: an
unrecognised ordinary key (e.g. `"nickname"`) is dropped by `pick()`, exactly as today, because a
file written by a *newer* build legitimately carries fields this build does not know — and the
`schemaVersion` gate is what makes that safe (a newer *format* is refused outright). Documented here
so the two policies are not confused: **unknown field ⇒ strip; forbidden key name ⇒ reject.**

**D4 — Caps are constants, exported, and server-side.** `MAX_FILE_DEPTH = 32` (a legitimate game is
`game → stages[] → tasks[] → smart/media/steps[] → object` ≈ 7 levels; 32 is generous and still
far below the ~10 000-frame stack) and `MAX_FILE_ARRAY_LEN = 1000` (the largest legitimate list is
`unlockAfterTaskIds`, bounded by `MAX_FILE_TASKS = 1000`). They live next to the existing
`MAX_FILE_*` constants and are enforced in the pure function, i.e. on the server, not only in the
Builder.

**D5 — Errors are bounded.** The scan stops after 25 findings and appends a "…and more problems"
line, so a hostile file cannot make the server build a megabyte-long error string. The existing
refusals already return early, so this only bounds the new walk.

**D6 — Field-type checks reuse the existing per-task pass.** The list/leaf type checks (C1–C4) go
into the loop that already validates each task, using small declarative tables, so no third traversal
is added. Where a check overlaps an existing one (`unlockAfterTaskIds` is already array-checked) the
existing check is extended rather than duplicated.

**D7 — No new user-facing UI string.** The Builder already renders `pre.errors.join(' · ')` through
its existing dialog and the callable's `invalid-argument` message through `b.importFailed`; both
labels are already in the `t.*` dictionaries. The new messages are *server-produced validation
detail* in the same English voice as every existing message in this module — identical to how
`gameStructureProblems` and `validateOrderItems` already report. Adding a parallel Hebrew catalogue
for this one module would leave the surrounding refusals half-translated; that is a separate,
module-wide job and is called out as such rather than started here. **No UI file is touched, so no
new PART B i18n finding can be introduced.**

**D8 — Reuse, don't re-derive.** `isValidCoord` (geo), `stripUnsafeDisplayChars`,
`validateUnlockGraph`, `validateAvailabilityWindow`, `validateOrderItems`, `validateSurveyChoices`
and `taskCompletabilityError` are all already wired in and are left exactly as they are. If a tags
normalizer exists in `packages/shared`, it is consumed (`normalizeTags` is already applied by the
callable) and not redefined here.

## Test Strategy

**Lane: pure vitest, no emulator.** `packages/shared` already runs `vitest run` (see
`popularity.test.ts`), and `npm test` picks it up through `turbo run test`. The validator is a pure
function of a parsed candidate object, so every case below is a direct call.

New file `packages/shared/src/gameFile.hardening.test.ts`, one `describe` per threat:

1. **Prototype pollution** — `__proto__`, `constructor`, `prototype` as a key (a) at the top of
   `game`, (b) inside `branding`/`scoringOptions`, (c) inside a stage, (d) inside a task, (e) inside
   `task.smart`, (f) inside `steps[0]`, (g) inside `media`. Each: `game === null`, the error names
   the key and its path, and `Object.prototype` is provably unpolluted after the call.
2. **Resource exhaustion** — 101 stages (existing), 1001 tasks (existing), `answers` /
   `choices` / `steps` / `unlockAfterTaskIds` over `MAX_FILE_ARRAY_LEN`, a multi-megabyte
   `description`, and an over-long `hint` and `title`. Each names its bound.
3. **Deep nesting** — a graph nested past `MAX_FILE_DEPTH`, passed both as an object and as raw JSON
   text, must **return** a depth error and must **not throw** (the assertion is wrapped so a
   `RangeError` fails the test loudly).
4. **Type confusion** — `answers: 5`, `answers: ["a", 5]`, `choices: {}`, `steps: "x"`,
   `steps: [1,2]`, `media: [1,2,3]` and a `media` object where the list belongs (`media` is
   `TaskMedia[]`), `description: 42`, `title: 7`, `stages: {}`, `game: []`,
   top-level array / `null` / number / string `"{}"`. Each is a named refusal; **and** for the
   `answers: 5` case a regression assertion that feeding the parser's output to
   `gameStructureProblems` no longer throws (the C1 500).
5. **Numeric poison** — `NaN`, `Infinity`, `-Infinity` (as literals and as `1e999` inside JSON text)
   on `numericAnswer`, `numericTolerance`, `geofenceRadiusMeters`, `hintPenalty`,
   `expiresAfterMinutes`, `pointValue`, `stage.requiredTaskCount`, and `coordinates.lat/lng`; plus
   out-of-range `lat: 91` / `lng: 181` (existing behaviour, asserted so it cannot regress).
6. **Identity / authz smuggling** — a document whose `game` carries `ownerUid: 'someone-else'`,
   `id`, `visibility: 'public'`, `playCount: 9999`, `deletedAt`, `integrationWebhookUrl`,
   `credits`/`wallet`, and a `runs` subcollection-shaped field: parse succeeds and **none** of those
   keys is present on the returned game. (The callable-side half — that the stored document has the
   caller's `ownerUid`, `visibility: 'private'`, `playCount: 0` — is the e2e assertion below.)
7. **Round-trip integrity (the positive case)** — a fully-loaded game with all nine task types,
   Hebrew/RTL titles, descriptions, clues and answers, emoji including a ZWJ sequence (placed in a
   `tag` / `steps[].answer`: titles and descriptions **are** deliberately run through
   `stripUnsafeDisplayChars`, which removes U+200D — pre-existing, intended behaviour), media, an
   unlock graph, availability windows, ordering and survey tasks: `serializeGameToFile` →
   `parseGameFile` returns it unchanged, with **zero** errors. This is the guard that the hardening
   refuses nothing legitimate. `scripts/test-game-file.ts` already property-tests the round trip over
   300 seeded games and must stay green untouched.

**Callable lane (written, not run).** New assertions are appended to the existing
`game-file-export-import` scenario in `scripts/e2e-verify.mjs`: a hand-edited file carrying
`ownerUid` of another account + `visibility: 'public'` + `playCount: 9999` imports as a game owned by
the caller, private, with `playCount: 0`; and a file with `answers: 5` is rejected with
`invalid-argument` (not `internal`). Per the task constraints these are **left unrun** — a live
playtest stack owns the emulator.

**Gates.** `npm run typecheck`, `npm run lint`, `npm test`, `npm run creator:build`,
`npm run play:build`. `npm run i18n:check` is not required (no UI file is touched, D7) but is run
anyway if any string surfaces in an app.
