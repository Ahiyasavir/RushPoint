## Context

The pre-launch audit found that `apps/play-web` — the participant-facing app — has two
critical runtime failure modes (requestNextTask swallowed, GPS error falls back to (0,0))
and one infinite-hang (GeofenceAuto), plus the entire TaskRunner and FinalScreen are
English-only in a Hebrew-first product. On the security side, `submitStationPhoto` accepts
arbitrary external URLs that could inject unvetted content into the staff review queue.

Current state before this change:
- `TaskRunner.tsx` routing `useEffect` (line 27-32): no `.catch`, no error UI.
- `withLocation` (line 343-350): `() => cb(0, 0)` on error — completely silent.
- `GeofenceAuto` `watchPosition` error cb (line 258): `() => undefined`.
- `TaskRunner.tsx`, `FinalScreen.tsx`: zero i18n — all literals hardcoded in English.
- `submitStationPhoto` in `functions/src/runs/index.ts`: no URL-origin check.
- `PhotoEntry`: `URL.createObjectURL` called but never revoked.
- `JoinScreen.submit()`: no client-side `required` field gate.
- `BuilderPage.tsx` `getGame` call: bare `void getGame(...)` with no error catch.
- `DistanceBadge`: `getCurrentPosition` (one-shot), never watches.
- `LocationPicker`: silent Nominatim fallback with no production warning.

## Goals / Non-Goals

**Goals:**
- GPS denial and network-error paths produce localized, actionable UI everywhere they occur.
- `TaskRunner` and `FinalScreen` are fully wired to `useT()` for HE/EN; zero new hardcoded
  string literals added.
- `submitStationPhoto` rejects URLs not beginning with the project's Firebase Storage origin.
- Object URLs created by `PhotoEntry` are revoked on cleanup.
- Required registration fields are caught client-side before `joinRun` is called.
- `BuilderPage` renders an error card on `getGame` failure.
- `DistanceBadge` uses a live `watchPosition` feed.
- `LocationPicker` warns visibly when running without a MapTiler key.

**Non-Goals:**
- No new Firestore schema, indexes, or security-rule changes.
- No structural redesign of TaskRunner or FinalScreen (layout preserved, strings migrated).
- No i18n for `StaffConsole`, `PlayScreen`, `NavMap`, or any creator-web screen.
- No retry logic beyond what is described in the spec (the retry button restarts the
  requestNextTask call; it does not implement exponential backoff).
- No server-side changes to `completeTask` GPS validation threshold (that is a separate
  concern from the client-side error UI).

## Decisions

### D1 — GPS error types: `LocationDenied` vs `LocationUnavailable`

`GeolocationPositionError` has three codes: PERMISSION_DENIED (1), POSITION_UNAVAILABLE (2),
TIMEOUT (3). We show a single localized "GPS unavailable" message for all three rather than
splitting into separate strings. **Rationale:** users on mobile typically can't distinguish
between "you denied permission" and "signal unavailable" — both require the same action
(enable GPS or contact host). A single clear message is better than three confusing ones.

### D2 — withLocation: warn-and-continue vs. hard-block

For `field` / `self_report` tasks, `withLocation` currently falls back to `(0, 0)`. After
this change it will call `onDenied()` instead of `cb(0, 0)`. The caller is responsible for
showing an error. We do NOT block the `field` / `self_report` submission entirely — those
task types may have `instant` or `locationless` trigger modes on the server, so the server
decides whether coordinates are required. The client surface is: show a warning, let the
user tap again to retry once they've enabled GPS. **Alternative considered:** hard-block
submission when GPS is denied. Rejected because it would break locationless field tasks
(trigger mode `instant`) where coordinates are optional.

New `withLocation` signature:
```ts
function withLocation(
  cb: (lat: number, lng: number) => void,
  onDenied?: () => void,
): void
```

### D3 — i18n namespace structure: `task` + `final` in existing i18n.ts

New keys go under `t.task.*` and `t.final.*` in `apps/play-web/src/i18n.ts`.
The `typeof HE` guard on `EN` already enforces compile-time parity. No new files needed.
**Alternative considered:** separate `taskI18n.ts` and `finalI18n.ts`. Rejected — adds
module split with no benefit; existing `i18n.ts` is not large enough to justify it.

### D4 — Photo URL validation: prefix check vs. Firebase Storage SDK

We validate `photoUrl` server-side with a `startsWith` prefix check in the callable:
`https://firebasestorage.googleapis.com/v0/b/rushpoint-pwa-7daaa.appspot.com/`
**Alternative considered:** using the Firebase Storage Admin SDK to `getMetadata` and verify
the file exists. Rejected — adds ~200ms latency per submission and a Storage SDK call just
to validate a URL we already trust was generated by our own `uploadTaskPhoto` helper. The
prefix check is sufficient to prevent arbitrary external URLs.

### D5 — DistanceBadge: watchPosition with 10s timeout

`watchPosition` with `{ enableHighAccuracy: true, maximumAge: 5000, timeout: 10000 }`.
The `useEffect` cleanup calls `clearWatch`. **Why not keep getCurrentPosition?** Because
as the participant walks toward the task, the badge showed a stale initial distance and never
updated — misleading UX.

### D6 — BuilderPage error: retry button calls getGame again

On `getGame` failure, render an error card: title "Could not load game", subtitle shows the
error message (Firebase-prefixed strings stripped), and a "Try again" button that re-runs
`getGame`. No router redirect. **Rationale:** the game likely exists (the user navigated to
it); a transient network error should be retryable in place.

## Risks / Trade-offs

- **D2 warn-and-continue:** Teams with `radius`/`exact` trigger tasks will still see a
  server error after warning them. The warning is UX improvement but not complete protection
  — the server is the authority. → Mitigation: the warning text says "GPS required for this
  task — enable location in your browser settings or contact your host."
- **D4 prefix check vs. SDK verify:** A well-constructed malicious URL matching the prefix
  pattern (impossible since the full path is server-controlled) could bypass the check. →
  Mitigation: the Firebase Storage rules already restrict writes to authenticated users under
  their run path, so a matching URL would have to come from a legitimate upload anyway.
- **i18n translation quality:** Hebrew copy for ~20 new keys must be reviewed by a native
  speaker before launch. → Mitigation: all HE strings are explicitly listed in the tasks.md
  so a single review pass can cover them.

## Migration Plan

Pure client and callable changes — no Firestore documents are modified. Deploy order:
1. Deploy `functions/` (new URL validation in `submitStationPhoto`) — backwards compatible
   since all existing in-flight submissions from the old client used Firebase Storage URLs.
2. Deploy `play-web` — new i18n keys, GPS error UX, object URL cleanup.
3. Deploy `creator-web` — BuilderPage error state, LocationPicker Nominatim warning.

Rollback: revert Firebase Functions deploy to the previous version; revert Vite apps.
