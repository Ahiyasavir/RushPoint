## 1. Product Overview

RushPoint is a **multi-tenant web platform** for building and running real-world team "field
game" experiences (scavenger-hunt / amazing-race style). Any creator signs up, designs a game
(ordered stages with geolocated or general tasks), launches a live run, shares an access code;
participants join on their phones, get routed between tasks, complete them, and are scored
automatically — **no human judge**.

**Three roles:**
- **Creator** — builds games, launches/runs them, manages billing. Real Firebase Auth (email/Google).
- **Participant** — joins a run with an access code, plays from their phone. Anonymous auth (`uid == teamId`).
- **Staff** — optional helper for a single run (photo review, SOS acknowledgement, announcements). Signs in with a one-time PIN that mints a scoped custom token.

*(🔭 v2.1: + RTDB 9000.)*

**Hard-won dev-script behavior (don't regress):**

## 4. Data Model — Firestore + RTDB

### 4.A — Firestore (source of truth for durable game state)

```
users/{ownerUid}                                                Creator profile (displayName, updatedAt)
users/{ownerUid}/games/{gameId}                                Private game template — Builder edits this
users/{ownerUid}/games/{gameId}/runs/{runId}                   Live run (CF-written only). Holds run.taskCounts{} routing counters.
       …/runs/{runId}/teams/{teamId}                           Participant state — teamId == participant uid (CF-written only)
       …/runs/{runId}/teams/{teamId}/taskStates/{taskId}       🔭 Planned — per-task progress (see §4.C)
       …/runs/{runId}/announcements/{id}                       Live announcements (read: any authed)
       …/runs/{runId}/flashMissions/{id}                       Timed bonus missions (read: any authed)
       …/runs/{runId}/alerts/{id}                              SOS / technical alerts ⚠️ collection is "alerts" in code
       …/runs/{runId}/teamLocations/{teamId}                   Live GPS pings (CURRENT). 🔭 v2.1: migrates to RTDB (see §4.B)
       …/runs/{runId}/staffInvites/{id}                        One-time staff PINs
publicGames/{gameId}                                           Denormalized gallery index (public read)
publicTasks/{gameId}_{taskId}                                  Task library entries (public read)
wallets/{uid}                                                  Creator credit/Pro ledger
wallets/{uid}/transactions/{txId}                              Payment history
accessCodes/{CODE}                                             Join code → {ownerUid, gameId, runId, status}
auditLogs/{id}                                                 Immutable admin trail (CF only)
```

> **Path-helper note:** Always use `FIRESTORE_PATHS` from `@rushpoint/shared`. One nuance: the
> SOS/alerts collection is literally `alerts` in the runtime code (`triggerSOS`, `acknowledgeAlert`,
> RunConsole, StaffConsole all read/write `…/runs/{runId}/alerts`), even though
> `COLLECTIONS.ADMIN_ALERTS` is named `adminAlerts`. The live path is `alerts`.

**Write policy — server-write-only state:** `firestore.rules` deny client writes to run / team /
score / leaderboard / wallet docs. Only Cloud Functions (Admin SDK) write them. To add a mutation:
write a callable in `functions/src/<domain>/index.ts` → re-export in `functions/src/index.ts` → add
a typed wrapper in the app's `services/calls.ts`. **Never a client write.**

**Current team-state storage (today):** a team's full progress — every stage and its tasks — lives
as a **nested `stages: RunStageRecord[]` array on the team document**. `completeTaskForTeam` rewrites
the **entire** `stages` array on each completion (a deliberate workaround: dotted-path updates into a
Firestore array coerce it to a map and corrupt the run — see [§23](#23-conventions--footguns)).

### 4.C — 🔭 Planned (v2.1): `taskStates` subcollection (resolve the stage-array overwrite risk)

> **🔭 Planned (v2.1) — Per-task subcollection.**
> **Current:** the whole `stages` array (all stages × all tasks) is overwritten on the parent team
> doc on **every** task completion.
> **Target:** deprecate storing full progress sequences as flat arrays on the parent team doc. Track
> per-task progress in a subcollection, one document per task:
>
> `users/{ownerUid}/games/{gameId}/runs/{runId}/teams/{teamId}/taskStates/{taskId}`
> *(shorthand in design docs: `runs/{runId}/teams/{teamId}/taskStates/{taskId}`)*
>
> ```ts
> interface TaskState {
>   taskId: string;
>   state: 'locked' | 'active' | 'completed';
>   completedAt?: Timestamp;
>   scoreAwarded: number;
>   attemptsCount: number;       // increments on each wrong answer / failed verify
>   startedAt?: Timestamp;       // for actualMinutes / velocity continuity
> }
> ```
>
> The team doc keeps only lightweight aggregates (`score`, `status`, `activeTaskId`, `bonusPenalty`,
> current stage pointer); per-task writes hit their own small documents.
> **Why:** avoids Firestore's **1 MB document-size limit** for long games (many stages × tasks),
> eliminates whole-array rewrites that cause **write contention / race conditions** and document
> lockups during fast-paced concurrent play, and lets two participants update two different tasks
> without contending on one doc. `FIRESTORE_PATHS` gains a `teamTaskState(...)` helper; `buildRankings`
> and routing read the subcollection (or a denormalized rollup) instead of the array.
> *(Migration: dual-write during rollout, then read-from-subcollection, then drop the array.)*

### 4.B — Realtime Database (RTDB) — 🔭 Planned (v2.1)

> **🔭 Planned (v2.1) — Offload live telemetry to RTDB.**
> **Current:** participants write continuous GPS to Firestore `…/runs/{runId}/teamLocations/{teamId}`
> roughly every 20 s via the `updateLocation` callable.
> **Target:** deprecate ephemeral coordinates in Firestore. All live telemetry moves to **Firebase
> Realtime Database**, written by the client over a low-latency WebSocket:
>
> ```
> /runs/{runId}/teams/{teamId}/location  →  { lat: number, lng: number, heading: number, updatedAt: number }
> ```
>
> RTDB security rules scope writes to the team's own `teamId` and reads to the run's owner/staff.
> The operator's live team map subscribes to `/runs/{runId}/teams` over RTDB; PII retention
> ([§15](#15-account-management--privacy)) deletes the run's RTDB subtree on prune.
> **Why:** RTDB bills by **bandwidth**, Firestore by **individual reads/writes**. Streaming the
> positions of dozens of active teams through Firestore is cost-inefficient and higher-latency than
> RTDB's persistent WebSocket. Durable results (scores/rankings) stay in Firestore; only ephemeral
> position data moves to RTDB.

## 5. Authentication & Authorization

- **creator-web** — real Firebase Auth (email/password + Google). The logged-out state is the
  marketing `AuthGate` (landing page). Captures `?ref=<uid>` for referrals.
- **play-web** — anonymous auth. The anonymous `uid` **is** the `teamId`. Persisted in a session.
- **Staff** — `inviteStaff` (owner-only) generates a 6-digit PIN stored under `staffInvites`.
  `staffSignIn(ownerUid, gameId, runId, pin)` validates the unused PIN, marks it used, and mints a
  **custom token** with claims `{ staff: true, staffName, permissions, ownerUid, gameId, runId }`.
  Staff then have a scoped Firestore read of exactly that one run's teams + alerts.

**Server-side auth guards (`functions/src/index.ts`):**
- `requireAuth(ctx)` — any signed-in user; returns uid.
- `assertAdmin(ctx)` — requires `token.admin` claim (bypassed in the emulator).
- `assertStaffOrOwner(ctx, ownerUid)` — passes if caller is the game owner, a platform admin, or
  staff whose token's `ownerUid` claim matches (bypassed in the emulator). Guards every live-ops
  mutation (announce, flash, ack SOS, review photo, adjust score).

### 5.A — 🔭 Planned (v2.1): Frictionless anonymous session recovery

> **🔭 Planned (v2.1) — Session Recovery Key.**
> **Current:** an anonymous uid lives in the browser's persisted session. If the participant loses it
> — opening the join link in an **in-app browser** (WhatsApp/Instagram) and then re-opening in
> Chrome/Safari, clearing storage, or switching devices — they become a **new anonymous user** and
> lose their team/progress.
> **Target:** on team creation, generate a short, unique **5-character `recoveryKey`** (e.g. `K7Q2M`,
> no confusable chars) stored on `…/teams/{teamId}`. play-web exposes a **"Recover my game"** flow
> where a player enters **GameCode + TeamName + RecoveryKey**; a new callable `recoverSession` verifies
> the triple and mints a **custom token bound to the original `teamId`**, re-attaching their progress
> to whatever browser they're now in.
> **Why:** the in-app-browser → native-browser hop is the single biggest drop-off in viral WhatsApp
> distribution. The recovery key makes an anonymous session portable without forcing account creation.
> **Security:** `recoveryKey` is verified server-side only, rate-limited, and never exposed in any
> participant-facing payload except the player's own confirmation screen.

## 6. Core Domain Model: Game → Stage → Task

### Game (template) — `users/{ownerUid}/games/{gameId}`
```ts
interface Game {
  id; ownerUid; title; description?;
  mode: 'individual' | 'team';
  pacing?: 'host' | 'self_paced';                 // 🔭 v2.1 — default 'host' (see §8)
  stages: Stage[];
  scoringPreset: 'time_only' | 'fixed_points_speed' | 'smart_weighted';
  scoringOptions?: { transitPenaltyEnabled?; sprintPenaltyEnabled? };
  registrationFields: RegistrationField[];        // always includes the required member "Name"
  branding?: { logoUrl?; primaryColor?; name? };  // primaryColor themes the play app
  visibility: 'private' | 'public';
  tags: string[];
  coverImage?; approxLocation?: { lat; lng; label? };
  playCount; createdAt; updatedAt;
}
```
`createGame` seeds an empty game (`stages: []`, `scoringPreset = fixed_points_speed`,
`registrationFields = [{name, member, required}]`, `visibility: private`).

### Stage
```ts
interface Stage {
  id; order; title;
  tasks: Task[];                  // 1+ tasks
  isFinal?: boolean;              // completing this stage finishes the team → Final screen
  requiredTaskCount?: number;     // partial completion: do N of M tasks (undefined = all)
}
```
- A stage unlocks the next stage (`order + 1`) when it completes.
- The first stage starts `active`; the rest start `locked`.
- **Stage completion rule:** complete when `completedCount >= required` OR all tasks are terminal.
  When it completes early (partial stage), the unfinished tasks are **auto-skipped** for that team.

### Task (embedded inside Stage — not a top-level doc)
```ts
interface Task {
  id; title; description?;
  type: TaskType;                  // see §7
  coordinates: { lat; lng };
  difficulty;                      // 1–10
  estimatedMinutes;
  expectedDurationMinutes?;        // used by fixed_points_speed bonus
  pointValue;
  maxConcurrentTeams;              // default 3 — station capacity for routing
  locationless?: boolean;          // no map pin / zero transit / done from anywhere
  hint?; hintPenalty?;             // paid hint (default 25 pts); text is SERVER-SECRET
  // type-specific (answer keys SERVER-SECRET — stripped from participant payload):
  choices?;                        // quiz: rendered as buttons if present
  answers?;                        // quiz: correct if any matches (trim + case-insensitive)
  numericAnswer?; numericTolerance?; // numeric: |entered − answer| ≤ tolerance (default 0)
  geofenceRadiusMeters?;           // geofence: auto-check-in radius (default 50m)
  steps?: TaskStep[];              // sequence: ordered sub-steps, each with optional secret answer
  smart?: SmartStationConfig;      // smart_station / photo config
  visionPrompt?: string;           // 🔭 v2.1 — photo task: Gemini Vision verification prompt (see §7)
  visionThreshold?: number;        // 🔭 v2.1 — confidence threshold to auto-pass (0–1, default 0.7)
  tags?;                           // library metadata
}
```

## 7. Task Types — Exact Behavior

The participant UI (`apps/play-web/src/components/TaskRunner.tsx`) renders a different control per
type. Every completion routes through `completeTaskForTeam` server-side (scores it + advances the
stage), then `releaseTask` (frees the station slot), then `assignNextInActiveStage`.

| Type | Builder authoring | Participant UI | Completion path | Verification |
|---|---|---|---|---|
| **`field`** | pin + "has location" | "I'm here" button | `completeTask` | none (🔭 v2.1: + velocity check, below) |
| **`self_report`** | — | "Mark complete" button | `completeTask` | none |
| **`smart_station`** | secret code (`smart.secretCode`) | code entry box | `verifyStationCode` → `completeTaskForTeam` | server compares code, trim + case-insensitive |
| **`photo`** | auto-approve toggle (🔭 v2.1: + AI vision prompt) | file picker (image, ≤12 MB) or pasted URL | `submitStationPhoto` → uploads to Storage | auto-approve completes instantly; **🔭 v2.1** AI vision auto-verifies; else staff `reviewStationSubmission(approved)` |
| **`quiz`** | choices (optional) + accepted `answers[]` | choice buttons OR free-text box | `submitTaskAnswer` | server matches any `answers[]`, trim + case-insensitive |
| **`numeric`** | correct number + ± tolerance | numeric box | `submitTaskAnswer` | `|entered − numericAnswer| ≤ numericTolerance` |
| **`geofence`** | auto-check-in radius (m) | `watchPosition` auto-fires when inside radius | `completeTask` (server re-validates GPS) | server: `haversineKm(gps, coords)*1000 ≤ radius`; rejects spoofs / "too far" (🔭 v2.1: + velocity check) |
| **`sequence`** | ordered `steps[]` (each prompt + optional answer) | one step at a time + progress bar | `submitSequenceStep(stepIndex, answer)` | per-step: blank answer = tap-to-confirm; else trim + case-insensitive; must be in order; task completes after last step |

**Server-secret sanitization (`sanitizeTaskForParticipant` in `runs/index.ts`):** `getMyTeamState`
strips `smart.secretCode`, `hint` text, `answers`, `numericAnswer`, each `steps[].answer`, and
(🔭 v2.1) `visionPrompt`/`visionThreshold` before sending. The client receives only `hasHint` +
`hintPenalty`, step `prompt`s (no answers), choices, tolerance, radius, and `smart.stationCoords`.
Answer keys never reach the device.

**Paid hints (`requestTaskHint`):** reveals `task.hint` for a point cost. Charged **once per
team/task** (transaction-guarded via `taskHintsUsed[]`); the cost is added to `bonusPenalty`. The
hint text is **never** in the task payload — only this callable returns it. Default cost 25.

### 7.A — 🔭 Planned (v2.1): Server-side GPS spoofing prevention (velocity validation)

> **🔭 Planned (v2.1) — Velocity validation in `completeTask`.**
> **Current:** `geofence` tasks validate a single distance — `haversineKm(gps, coords)*1000 ≤ radius`
> — but a forged GPS coordinate within the radius is accepted, and there's no check against
> teleporting across the map.
> **Target:** any **coordinate-bearing completion** (`geofence`, located `field`) runs **velocity
> validation** server-side against the team's previously logged coordinate (kept on the team doc /
> taskState, or read from RTDB):
>
> ```
>            distance(Coord_new, Coord_prev)
> speed  =  ────────────────────────────────
>                  time_new − time_prev
> ```
>
> If `speed` exceeds a physical limit (e.g. **> 30 km/h** in non-driving modes) or is an impossible
> instant teleport (Δtime ≈ 0 over a large Δdistance), the server **flags the team "Abnormal
> Movement"**: it does **not** silently reject (GPS jitter is real), but records the flag on the team,
> raises an `alerts` entry of type `'abnormal_movement'`, and surfaces it on the operator + staff
> consoles for a human decision. A confirmed cheat can be skipped / score-adjusted via existing tools.
> **Why:** closes the "fake-GPS app" hole that pure radius checks leave open, without punishing
> legitimate players for noisy phone GPS.

### 7.B — 🔭 Planned (v2.1): Automated AI photo verification (Gemini Vision)

> **🔭 Planned (v2.1) — Gemini Vision auto-verification for `photo` tasks.**
> **Current:** a `photo` task either `autoApprove`s blindly or waits for a human (`reviewStationSubmission`).
> **Target:** the creator authors a natural-language **`visionPrompt`** on a photo task (e.g.
> *"Verify this image contains at least 3 people smiling near a green statue"*) and an optional
> `visionThreshold` (default 0.7). On `submitStationPhoto`, a Cloud Function calls the **Google Gemini
> Vision API** (server-side only — API key in `functions/.env`, never in any client bundle), receives
> a structured `{ pass: boolean, confidence: number, reason: string }`, and:
> - `confidence ≥ visionThreshold` → auto-completes the task instantly (`completeTaskForTeam`).
> - below threshold → marks the submission `rejected` with the model's reason, OR (creator option)
>   **falls back to staff review** so vision never hard-blocks a legitimate photo.
> **Why:** eliminates the manual photo-review bottleneck for large-scale games where staff can't keep
> up with dozens of teams. Staff review remains available as the fallback and for vision-disabled tasks.
> **Cost/limits:** vision calls are metered; the function caps retries and logs token spend. Vision is
> **opt-in per task** (only when `visionPrompt` is set).

## 8. The Run Lifecycle

```
Creator: launchRun(gameId)  →  bills a free run / credit, creates Run(status:'live') + accessCode
Participant: getJoinInfo(code)  →  renders the registration form (title, branding, fields)
Participant: joinRun(code, displayName, members)  →  RunTeam(status:'registered', launched:false)
Creator: startTeams(gameId, runId)  →  all teams launched:true, status:'active', first stage active, first task assigned
   (🔭 v2.1 self-paced mode: joinRun launches the team immediately — no startTeams; see §8.A)
Participant plays  →  completeTask / verifyStationCode / submitTaskAnswer / submitSequenceStep / photo
   each completion: score task → advance/unlock stage → auto-assign next task
   (🔭 v2.1: per-task writes hit the taskStates subcollection §4.C; coordinate tasks run velocity validation §7.A)
Creator: refreshLeaderboard (optional, mid-run, staged reveal via publish flag)
Creator: finalizeRun(gameId, runId)  →  Run(status:'finished'), final leaderboard computed + published
```

### `launchRun` (billing transaction)
Runs inside a Firestore transaction so a double-launch can't double-spend. Order of precedence:
1. **Pro plan** → `billingType: 'pro'`, `maxParticipants: 50`. No charge.
2. **Free run available** (`lifetimeFreeRunsUsed < 3 + bonusFreeRuns`) → consume one (increment
   `lifetimeFreeRunsUsed`, log `free_run_consumed` tx), `billingType: 'free'`, `maxParticipants: 5`.
3. **Event Credits > 0** → consume one (decrement `eventCredits`, log `charge_event` tx),
   `billingType: 'credit'`, `maxParticipants: lastPackageMaxParticipants`.
4. Else → `resource-exhausted` error ("No Event Credits left…").

Then writes the `Run` doc + `accessCodes/{CODE}` doc in a batch, and best-effort increments
`game.playCount`. Access codes are 6-char, no confusable characters (`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`),
uniqueness-checked up to 10 attempts.

> **🔭 Planned (v2.1) — Game snapshot on launch.**
> **Current:** `launchRun` reads the live game template at launch time. If the creator edits the
> game template while a run is in progress, the run's active stage/task definitions can drift.
> **Target:** at launch time, copy the full `stages[]` + `tasks[]` structure into the `Run` doc
> itself (a `gameSnapshot` field), and lock the game from edits while the run is live (or show a
> prominent warning). All run-time reads (`completeTaskForTeam`, routing, scoring) use
> `run.gameSnapshot` instead of the live game template.
> **Why:** correctness — editing a template mid-run currently silently corrupts routing and
> scoring for in-flight teams. A snapshot makes the run hermetically sealed at launch time.

### `joinRun`
- Looks up the access code; rejects `revoked` codes and `finished` runs.
- **Idempotent:** if the team already exists, returns `{ alreadyJoined: true }`.
- Builds initial stage records from the game template (`buildInitialStages`): first stage `active`,
  rest `locked`, all tasks `unassigned`, `requiredTaskCount` clamped to `[1, tasks.length]`.
  *(🔭 v2.1: also seeds the `taskStates` subcollection and a `recoveryKey` on the team.)*
- **Capacity is a hard ceiling enforced in a transaction** — concurrent joins can't overshoot
  `maxParticipants`. Over-cap → `resource-exhausted` ("This free run is full (5)…" / "This run is full…").
  There is **no per-participant billing** — the run was paid for at launch.

### `startTeams`
Owner-only. Marks all (or specific `teamIds`) registered teams `launched: true`, `status: 'active'`,
stamps `startedAt`, marks the first stage `startedAt`, then assigns each team's first task via
`assignNextInActiveStage` (using a default Jerusalem-ish coordinate as the team's initial location).

### 8.A — 🔭 Planned (v2.1): Hostless / self-paced "play anytime" run mode

> **🔭 Planned (v2.1) — Self-paced (asynchronous) runs.** Maps to Appendix B #5.
> **Current:** every run is **host-driven** — participants register and **wait** in a "Waiting for the
> host to start…" state until the creator clicks **Start all teams** (`startTeams`). The host is a hard
> launch bottleneck: nobody can play a published game until a human presses Start.
> **Target:** a creator can mark a game **"play anytime"** so each participant's run begins the moment
> *they* join — no host, no waiting screen. Implemented as `Game.pacing: 'host' | 'self_paced'`.
>
> **Exact requirements (the contract the tests pin down):**
> 1. **Data model.** `Game.pacing?: 'host' | 'self_paced'`, **default `'host'`**. **Unset ⇒ `'host'`**
>    (back-compat: every existing game keeps today's behavior with no migration). A single pure
>    resolver (`resolvePacing(game) → 'host' | 'self_paced'`) is the only place the default is applied,
>    so backend and UI can never disagree.
> 2. **Self-paced join launches the team.** In a `self_paced` run, `joinRun` — *after* registering the
>    `RunTeam` — immediately launches **only that team**: `launched: true`, `status: 'active'`,
>    `startedAt = now`, first stage `active`, and the first task assigned via the **same**
>    `assignNextInActiveStage` path `startTeams` uses (no duplicated routing logic).
> 3. **No host action required.** A `self_paced` team is fully playable with **zero** `startTeams`
>    calls. `startTeams` on a `self_paced` run is a **safe idempotent no-op** for already-launched
>    teams (it must never re-stamp `startedAt` or re-assign the first task — that would reset a team's
>    clock and corrupt scoring).
> 4. **Per-team clock (not a shared gun).** Scoring/elapsed time is measured from **each team's own
>    `startedAt`** (already how `completeTaskForTeam` computes `actualMinutes`). Two teams that join an
>    hour apart are each scored relative to their own start; the live + final leaderboard compare
>    per-team performance, never wall-clock-since-launch.
> 5. **Idempotent re-join is unaffected.** Re-calling `joinRun` for an existing team still returns
>    `{ alreadyJoined: true }` and **must not** re-launch, re-stamp `startedAt`, or re-assign a task.
> 6. **Capacity still enforced.** A drop-in run can fill: `joinRun` rejects with `resource-exhausted`
>    once `maxParticipants` (the billing-tier cap from `launchRun`) is reached — same cap as host mode.
> 7. **Routing start coordinate.** Host launch uses a fixed start coord; self-paced has no host-chosen
>    gun position, so the first-task assignment uses the **participant's join location** when provided,
>    else falls back to the game's first-task / start location — **never** a hardcoded city center.
> 8. **Finish & lifecycle.** `finished` runs still reject new joins (existing rule). The owner ends an
>    always-on run with `finalizeRun` like any other; a `self_paced` run simply has no "start" step.
> 9. **Play-web UX.** A `self_paced` participant **never sees** the "Waiting for the host…" screen —
>    `joinRun` returns a launched team, so `PlayScreen` lands directly on the first task.
> 10. **Builder UX.** The Builder Settings step exposes a **pacing toggle** (host-driven vs play-anytime)
>     with copy explaining the tradeoff (synchronized competition vs always-on drop-in).
> 11. **Staged rollout.** Self-paced is gated behind the launch **feature flag** (§26.6 / Appendix B
>     #34) so it can ship dark and be enabled deliberately.
>
> **Why:** unlocks always-on, drop-in experiences (museum trails, campus tours, "play anytime"
> marketing games) and removes the host as a launch bottleneck — a core driver of the viral, no-setup
> growth loop. Host-driven mode stays the default for synchronized competitive events.

### Task completion (`completeTaskForTeam`)
Transaction on the team doc. **Idempotent** (returns early if the task is already `completed`). Steps:
1. Find the task in the team's stage records *(🔭 v2.1: in the `taskStates` subcollection)*.
2. Compute `actualMinutes` from `taskRec.startedAt` (or team `startedAt`).
3. *(🔭 v2.1: for coordinate tasks, run velocity validation §7.A before accepting.)*
4. Score the task by preset (`time_only`→0, `fixed_points_speed`→`pointValue`, `smart_weighted`→sigmoid).
5. Mark task `completed` with `earnedScore` + `scoreBreakdown` *(🔭 v2.1: `scoreAwarded`/`attemptsCount` on the taskState doc)*.
6. **Stage completion check** (see §6) — auto-skip leftover tasks, mark stage `completed`, set
   `earnedScore`. If the stage is `isFinal` (or last), the team finishes; else unlock the next stage.
7. If **all** stages complete → `status: 'finished'`, `finishedAt`. Always clear `activeTaskId`.

### `skipStage`
Owner-only escape hatch. Skips every pending task in the team's active stage with a fair
`skipAward` per preset (`time_only`→0, `fixed_points_speed`→`pointValue`, `smart_weighted`→on-target
sigmoid). Completes the stage, unlocks the next (or finishes the team).

### `finalizeRun` & `refreshLeaderboard`
Both call the **shared** `buildRankings(game, teams, now)` so live and final standings never drift.
- `finalizeRun` — sets `status: 'finished'`, `finishedAt`, writes leaderboard **published: true**.
- `refreshLeaderboard` — recomputes mid-run **without** ending it. `publish` + `frozen` flags are
  preserved unless explicitly changed (staged reveal — organizers always see it; participants only
  after `publish`).
- `getPublicLeaderboard(code)` — anyone signed in can fetch standings by access code, but only
  returns `rankings` once `published` (otherwise empty). Used by the shareable `?board=` link.

> **🔭 Planned (v2.1) — `getMyTeamState` response versioning.**
> **Current:** PlayScreen uses a dual pattern — `onSnapshot` on the team doc triggers an immediate
> `getMyTeamState` RPC call, **plus** an independent 12-second poll. Both paths are unbounded and
> can return out-of-order. A stale poll arriving after a fresh snapshot reverts visible state.
> **Target:** (1) **remove the 12-second poll** — `onSnapshot` already delivers real-time updates;
> the poll is redundant and causes ~5 extra RPCs/minute per participant. (2) Add a
> monotonically-increasing `stateVersion` (or `updatedAt` timestamp) to `MyTeamState`; the client
> discards any response older than the last applied version.
> **Why:** eliminates the most common source of "UI flickering back" during active play, cuts
> Firebase Function invocations by ~80% per participant, and removes a battery-draining background
> wake cycle. The `onSnapshot` trigger is already real-time; the poll adds nothing but noise.

## 9. Smart Routing Algorithm

File: `functions/src/routing/assignNextTask.ts`. Operates on the tasks **within one stage**. If a
stage has a single task, the caller assigns it directly (no routing). Multi-task stages route.

**Priority formula (preset-aware):**

`smart_weighted` (skill-aware):
```
priority = 0.5·Φ − 0.3·TransitNorm + 0.2·Ω
```
`fixed_points_speed` / `time_only` (nearest available, no skill):
```
priority = 0.6·Φ − 0.4·TransitNorm
```

Where:
- **Φ (load factor)** = `(maxConcurrentTeams − currentCount) / maxConcurrentTeams` — 1 = empty, 0 = full.
- **TransitNorm** = `min(transitMinutes, 30) / 30`. `transitMinutes = haversineKm × 12` (5 km/h walk).
  A `locationless` task has transit **0**; a task with invalid coords defaults to 5 min.
- **Ω (skill match)** = `1 − |skillRatio − normalizedDifficulty|`, where `normalizedDifficulty = (difficulty − 5)/5`.

**Skill ratio (`computeSkillRatio`):** the team's historical pace, `S ∈ [−1, 1]`. For each completed
task, `clamp((actualMinutes − estimatedMinutes) / estimatedMinutes, −1, 1)`, averaged. Negative =
consistently faster than estimate; positive = slower. New teams start at 0.

**Station occupancy counters:** stored as a flat map `run.taskCounts[taskId]` on the Run doc.
`assignTask` filters out completed / `paused` / `closed` / full tasks, sorts candidates by priority,
picks the top, and **atomically increments** `taskCounts[taskId]`. `releaseTask` decrements it on
completion or `checkOutTask`. `getRecommendedTasks` returns a read-only ranked top-5 (no assignment).

## 10. Scoring System

Three fully-automatic presets (`packages/shared/src/scoringPresets.ts`). No human input. Used in
two places: the creator preview, and the server (`completeTaskForTeam` per-task + `buildRankings` final).

### Per-task score (at completion time)
- **`time_only`** — 0 (ranking is purely by elapsed time).
- **`fixed_points_speed`** — `task.pointValue`.
- **`smart_weighted`** — `100 × (difficulty/10) × sigmoid(actual/estimated)`, where
  `sigmoid(x) = 0.2 + 1.3 / (1 + e^(3(x−1)))`. On-target (x=1) ≈ multiplier 0.85; much faster → up to ~1.5; much slower → 0.2.

### Final ranking (`buildRankings`)
For each team:
```
raw = presetTotal                       // sum of task earnedScore (or 0 for time_only)
raw = applyCompletionBonus(raw, stages) // +500 if every stage completed
raw = applyPenalties(raw, bonusPenalty) // − hints − fines, floored at 0
```
Then, for non-`time_only` presets with ≥2 **finished** teams, a **Z-Score time bonus** is applied to
finished teams: `score + round(−z × 200)`, where `z = (teamDurationMin − μ) / σ` across finishers
(faster than average → bonus; 1σ ≈ ±200 pts), floored at 0.

**Sort order:**
- `time_only` — finished teams by `durationSeconds` ascending; unfinished sink, broken by `completedStages`.
- Others — by final `score` descending.

### `bonusPenalty`
A single accumulator subtracted at the end. Increased by paid hints (`requestTaskHint`) and by
`adjustTeamScore` (a `−bonus` / `+fine`; the callable stores `newPenalty = prev − delta`, so a
positive delta is a bonus that *reduces* the penalty). Every adjustment writes an `auditLogs` entry.

### Optional opt-in penalties (`Game.scoringOptions`)
`transitPenalty` (exponential late-arrival, cap 500) and `sprintPenalty` (exponential timed-stage
late, cap 300) exist in shared + `scoring/calculateScore.ts`. **Note:** `calculateScore.ts` also
contains v1-era helpers (8-slot completion bonus, green-slot tie-breaker `computeTieMetrics` /
`compareForRanking`) that are unit-tested but **not wired into the v2 `buildRankings` path** — the
live final ranking is the Z-Score model above.

> **🔭 Planned (v2.1) — Frontend performance fixes.**
> Three quick-win issues identified in the play-web client:
> - **Dual `watchPosition` watchers:** both `PlayScreen` and `TaskRunner` independently register
>   `watchPosition({ enableHighAccuracy: true })`. Two simultaneous watchers drain battery and
>   create racing coordinate updates. **Fix:** single watcher in `PlayScreen`; coords passed down
>   as props/context to `TaskRunner` and `NavMap`.
> - **`NavMap` `JSON.stringify` dependency:** the `useEffect` that rebuilds map markers uses
>   `JSON.stringify(targets)` as its dependency — O(N) every render even when targets haven't
>   changed. **Fix:** replace with a `useMemo` over the target array, keyed by id/coord.
> - **`LiveOps` 1-second tick:** `setInterval(1000)` calls `setState` once per second to expire
>   flash-mission banners — causes the entire `LiveOps` tree to re-render 60×/minute.
>   **Fix:** compute expiry on render with `Date.now()` via `useRef` + a single timeout per
>   mission, eliminating the continuous tick.
> Together these reduce battery drain and unnecessary re-renders during active play.

  entirely in self-paced runs — the team is launched on join.)*
- **Racing state**: header (branded, themed by `branding.primaryColor`), stage progress bar,

- **Finished state** → `FinalScreen`: trophy, final score, rank/medal, "race wrapped" stats, share

> gives "which way + how far" at a fraction of the cost and keeps phones alive to the finish line.

## 21. Offline, PWA & Resilience

- Firestore `persistentLocalCache` (reads survive network drops).
- Service worker (Vite PWA) — offline app shell; registered in prod `main.tsx`.
- `ConnectionBanner` — visible offline indicator.
- `ErrorBoundary` (both apps) — crash containment.
- `useWakeLock` — screen stays awake while racing.
- Geolocation always falls back gracefully (0,0 / silent catch) so a denied permission never blocks.
- **MapLibre is lazy-loaded** (`React.lazy`) — kept out of the initial bundle.

> **🔭 Planned (v2.1) — Battery-Saver Compass mode** ([§19.B](#19b--planned-v21-battery-saver-compass-mode))
> is a first-class PWA capability: a toggle that **fully unmounts** the WebGL map and runs a pure-SVG
> compass, dramatically cutting CPU/GPU/battery use on long outdoor runs. Combined with RTDB telemetry
> (fewer expensive Firestore round-trips) and the existing wake-lock/offline cache, it targets
> all-day battery survival on a mid-range phone.

> **🔭 Planned (v2.1) — PWA Web Push notifications.**
> **Current:** participants must keep the play-web tab open and active to receive announcements,
> flash missions, or "your stage unlocked" events — there is no background delivery.
> **Target:** on join/start, request `Notification` permission and register a **Web Push
> subscription** (via the service worker's `pushManager.subscribe`). Cloud Functions can then send
> targeted pushes via the FCM HTTP v1 API: `onSnapshot` triggers in `startTeams` / stage unlock /
> `pushAnnouncement` → FCM → device notification. Graceful fallback if permission denied.
> **Why:** keeps participants engaged even when the phone screen is off; critical for events where
> teams separate and need to know when the next stage opens.

> **🔭 Planned (v2.1) — Offline mutation queue for critical task submissions.**
> **Current:** if the network drops while a participant submits a task answer or check-in, the
> callable fails with a network error. There is no retry — the team is stuck until a page reload.
> **Target:** wrap `completeTask` / `submitTaskAnswer` / `submitSequenceStep` in a lightweight
> **IndexedDB retry queue**: mutations are written locally before the RPC, marked as `pending`;
> a `sync` event (or online listener) drains the queue when connectivity resumes. Duplicate
> guards in the callables (already idempotent) absorb any double-submissions.
> **Why:** outdoor events have patchy cellular; losing progress to a 2-second network hiccup is
> the single most frustrating experience a participant can have mid-race.

### 21.A — 🔭 Planned (v2.1): Performance Budgets & "buttery smooth" UX

> **Goal:** the app must feel instant and jank-free on a mid-range phone over mobile data.
> **HARD REQUIREMENT — no route may take more than 2.5s to become usable (LCP).** This is a
> ceiling, not an average. These budgets are a **contract in code** — `packages/shared/src/perfBudget.ts`
> (`TIMING_BUDGET_MS`, `BUNDLE_BUDGET_KB`, `CLS_BUDGET` + `isWithin*Budget` predicates) — so the app,
> the build gate, and the test suite all measure against the same numbers.

**The budget (single source of truth — `perfBudget.ts`):**

| Metric | Budget | Why |
|---|---|---|
| **LCP** (page load) | **≤ 2500 ms** | The hard requirement. Also the CWV "good" ceiling. |
| FCP | ≤ 1800 ms | Something meaningful on screen fast. |
| TBT | ≤ 200 ms | Main thread not blocked during load. |
| **INP** (interaction) | **≤ 200 ms** | Taps feel instant — the core of "no jank". |
| CLS | ≤ 0.1 | No layout jump as content loads. |
| Route transition | ≤ 300 ms | In-app nav feels instant. |
| Long task | < 50 ms | Anything longer stutters the main thread. |
| Frame | ≤ 16.7 ms | 60fps. |
| Initial JS (gz) | ≤ 200 KB | Small critical path → fast LCP. |
| Initial transfer (gz) | ≤ 300 KB | Total bytes to first interaction. |
| Lazy chunk (gz) | ≤ 150 KB | Each on-demand feature stays cheap. |

**How we hit ≤ 2.5s load (efficient + robust, in priority order):**
1. **Tiny critical path.** Every route is `React.lazy`; MapLibre and the story-card canvas are
   lazy-only and **must never appear in an initial chunk** (build gate enforces it). `preconnect` to
   Firebase + MapTiler.
2. **Cache-first paint.** Firestore `persistentLocalCache` + the SW app-shell precache → repeat
   visits paint from cache (≤ 1s) and revalidate in the background (stale-while-revalidate). PlayScreen
   renders cached team state immediately, then reconciles.
3. **Skeletons, not spinners.** Every async surface reserves its final layout (zero CLS); no
   layout-shifting loaders.
4. **Cold-start avoidance.** Hot callables (`getMyTeamState`, `getJoinInfo`) keep payloads small and
   use min-instances; the snapshot/versioning/poll-removal work (§8, Appendix B #11/#17/#18) slashes
   call volume so the network is rarely on the critical path.
5. **Font/asset discipline.** Self-hosted fonts with `font-display: swap`; images sized + lazy.

**How we stay smooth at runtime (INP ≤ 200ms, 60fps):**
- The four perf quick-wins (Appendix B #11–#14): drop the redundant poll, single geolocation watcher,
  `NavMap` `useMemo`, `LiveOps` per-mission timeout.
- **Optimistic UI** on task submit — show success instantly, reconcile on server confirm (pairs with
  the offline queue's idempotent replays).
- **Virtualized** long lists (RunConsole teams, leaderboard) so 100+ rows scroll at 60fps.
- Heavy work off the main thread (story-card canvas → OffscreenCanvas/worker); non-urgent work
  (telemetry, prefetch) via `requestIdleCallback`; `content-visibility: auto` for offscreen sections.
- **GPU-only transitions** (animate `transform`/`opacity`, never layout props); prefetch the likely
  next route chunk on intent; everything honors `prefers-reduced-motion`.

**How it's proven (the test target):** the deterministic contract is gated **today** by
`scripts/test-perf-budget.ts` (pins LCP = 2500 ms, the predicates, and the budget invariants — see
[§24](#24-testing--gates)). The **measured** numbers — real LCP/INP/CLS in the browser and real
gzipped bundle sizes from the Vite manifest — are the RED targets in
`functions/src/__planned__/v21-performance-and-smoothness.todo.test.ts` (Appendix B #23–#25),
verified via the preview tools and the build gate as those changes ship.

## 23. Conventions & Footguns

**Firestore**
- **Server-only state:** never write run/team/score/leaderboard/wallet from a client — rules block it.
- **`.set({merge})` + dotted keys is a footgun:** `{['a.b']: v}` writes a *literal* top-level field
  named `"a.b"`, NOT a nested path. Use a real nested object. (`.update()` dotted keys ARE nested
  paths — but **never dotted-update an array element**; it coerces the array into a map keyed
  `"0","1",…` and breaks the run flow. `completeTaskForTeam` / routing always rewrite the **full**
  `stages` array for this reason — and [§4.C](#4c--planned-v21-taskstates-subcollection-resolve-the-stage-array-overwrite-risk)
  is the v2.1 fix that removes the array entirely.)
- **No compound queries** needing custom indexes — filter/sort in memory (gallery search does this).
- **🔭 v2.1 — Don't grow arrays on a parent doc:** unbounded sequences (per-task progress) go in a
  **subcollection**, not a flat array on the team doc (1 MB limit + write contention).
- **🔭 v2.1 — Don't put ephemeral high-frequency data in Firestore:** live GPS belongs in **RTDB**
  (bandwidth-billed), not Firestore (per-write-billed).

**Frontend**
- **Tailwind:** static class strings only (no `bg-${x}`). play-web reverses the zinc scale so
  `text-zinc-100` reads dark-on-light. Prefer logical classes (`ms-`, `text-start`) for RTL.
  *(Dynamic per-game color uses inline `style` with `branding.primaryColor`, never a templated class.)*
- **RTL / i18n:** user-authored content uses `dir="auto"`. creator-web is Hebrew by default;
  `/settings` switches to English. Announcements/flash missions are bilingual (EN + HE fields).
- **Answer-key secrecy:** the participant sanitizer strips every answer key; the client only ever
  learns `hasHint` + cost, never the hint text / code / answers / vision prompt.
- **🔭 v2.1 — Server-trust coordinates:** never trust a client-asserted check-in; the server
  re-validates distance AND velocity ([§7.A](#7a--planned-v21-server-side-gps-spoofing-prevention-velocity-validation)).
- **🔭 v2.1 — Secrets stay server-side:** the Gemini API key lives in `functions/.env`; vision calls
  happen only inside Cloud Functions, never the client.

**Emulator:** Java ≥ 21 (launcher auto-switches); connect via `127.0.0.1`; Ctrl+C to persist.
**Bundle:** keep MapLibre behind `React.lazy`.

**Environment files** (all gitignored; emulator-safe defaults baked into client configs):
```
apps/creator-web/.env   VITE_FIREBASE_* (+ VITE_MAPTILER_KEY, VITE_PLAY_URL)
apps/play-web/.env      VITE_FIREBASE_* (+ VITE_MAPTILER_KEY, VITE_CREATOR_URL, 🔭 VITE_RTDB_URL)

## 26. Launch Hardening & Compliance

These items close the gap between *feature-complete* and *safe to launch to the public*. They are
not new gameplay — they are the production, security, trust, and legal layer. Indexed in
[Appendix B](#appendix-b--v21-roadmap--planned-architecture-changes) rows 26–36.

### 26.0 — Security & storage rules verification suite ✅ **shipped**

The entire anti-cheat + multi-tenant model rests on `firestore.rules` + `storage.rules` — and it is
now **directly tested**. `scripts/test-rules.mjs` (`npm run test:rules`, emulator-bound like
`npm run e2e`, using `@firebase/rules-unit-testing`) asserts against the **real** rules that:
- **Server-write-only holds:** a client (even the owner) **cannot** write run/team/score/wallet/alert/
  publicGames/auditLogs docs; the default-deny rule blocks any unmatched path.
- **Tenant isolation holds:** a user can't read another creator's profile/games/wallet; a participant
  reads **only its own** team doc, never a sibling team's.
- **Staff scoping holds:** a staff custom token reads only the one run it was minted for.
- **Public/join reads** behave (publicGames world-readable; accessCodes auth-only).
- **Storage:** a team uploads only into its own folder, image-only, < 10 MB; the CF-only `stream/` is
  unwritable by clients; photo reads require auth.
> ⚠️ This is **not** in the always-green `npm test` (it needs the emulator). Run it in CI / pre-deploy
> so a rules regression blocks release — it is the highest-leverage launch test.

### 26.1 — 🔭 App Check (abuse prevention)
Gate **every** callable + Storage write behind Firebase **App Check** (reCAPTCHA v3 on web). Without
it the public anonymous endpoints can be scripted (brute-force access codes, fake completions). Pairs
with per-uid rate limiting ([Appendix B #19](#functional-gaps-new-capabilities)).

### 26.2 — 🔭 Production observability
Wire the existing crash-report **seam** (`services/telemetry.ts` → `setCrashReporter`) to a real sink
(Sentry); structured CF logs with run/owner context (no PII); **alerting** on CF error rate +
`stripeWebhook` failures; a **scheduled daily Firestore export** (backup) with a documented restore
(DR); uptime monitoring on a health endpoint ([§26.6](#266--launch-smoke-health-check--kill-switch)).

### 26.3 — 🔭 Transactional email
A server-only provider adapter (e.g. SendGrid; key in `functions/.env`). **Receipts/invoices** on every
purchase/Pro charge (Israeli tax compliance), optional **run-summary** email on `finalizeRun`, and
password-reset for email/password creators. Idempotent sends (no dupes on webhook retry) with a
delivery log.

### 26.A — Operator mailing-list export (✅ **shipped** as a server script)
> **What you asked for:** *not* an in-app sending system (that would just confuse users) — instead a
> simple way for **you, the platform operator**, to get the registered emails as **comma-separated
> lists** you can paste into the **BCC** of a normal email (Gmail/Outlook) and send yourself.
> **Shape (shipped):** `scripts/export-emails.mjs` (`npm run emails:export`) — a server-side admin
> script (firebase-admin) that joins every Auth email with its consent flags and prints **three
> comma-separated lists**:
> 1. **marketing** — consented to ads/promotions (`marketingConsent === true`)
> 2. **updates-only** — declined ads but OK with important updates (`updatesConsent === true`)
> 3. **combined** — everyone reachable (1 ∪ 2)
>
> De-duplicated + sorted; counts printed; `--out file.txt` to save; runs against the emulator by
> default or `--prod` with a service-account key. Anyone with **no consent**, no email, or flagged a
> **minor** is excluded from every list (and counted).
> **Compliance (non-negotiable):** marketing email in Israel is **opt-in** (חוק התקשורת/anti-spam). The
> consent flags live on `users/{uid}` — **`marketingConsent`** + **`updatesConsent`** (both default
> off, captured explicitly at signup/Settings; the capture UI + an unsubscribe path are the remaining
> 🔭 work, see Appendix B #30). The export only ever reflects current consent, so flipping a user's flag
> (or their unsubscribe) removes them from the next export. When you paste into your mail client, send
> as **BCC** and include an unsubscribe line. Transactional mail ([§26.3](#263--transactional-email)) is
> separate and not gated by marketing consent.

### 26.4 — 🔭 Minors & guardian consent
Launch wedges (bar-mitzvah, youth groups) skew **under-18** — a real legal gate in IL. Join
registration captures an age band / guardian-consent flag where the game requires it; a run that "may

contention — and validating the `taskStates` migration ([Appendix B #1](#41--…)) under load. A

**maintenance kill-switch** flag (graceful read-only mode) and **feature flags** for staged rollout of

### 26.9 — 🔭 Authorization & anti-cheat hardening (launch-gating)

> **OpenSpec change:** [`openspec/changes/auth-anticheat-hardening/`](openspec/changes/auth-anticheat-hardening/).
> Found in the 2026-06-25 production audit by reading the live callables, `firestore.rules`, and the
> payments path. These are **server-side authorization correctness** gaps — the highest-leverage
> launch blockers after §26.0. Each is verified in `scripts/test-rules.mjs` and/or `scripts/e2e-verify.mjs`.

**The cluster (Appendix B rows 38–44):**

1. **🚨 IDOR on the station callables (P0, row 38).** `submitStationPhoto` and `verifyStationCode`
   (root `functions/src/index.ts`) take `teamId` from the **request payload** and never check it
   equals `context.auth.uid`. `submitStationPhoto` has **no** team-ownership check at all — any
   anonymous user can submit a photo for any `teamId` in any run whose `{ownerUid,gameId,runId}` they
   know, and an `autoApprove` task then calls `completeTaskForTeam`, **advancing another team**.
   Every callable in `runs/index.ts` already derives `teamId = requireAuth(context)` correctly; these
   two are the inconsistency. **Fix:** derive the acting team from the token; reject a mismatched
   payload `teamId` with `permission-denied`.

2. **🚨 Access-code enumeration (P0, row 39).** `match /accessCodes/{code} { allow read }` grants
   both `get` **and `list`** — a client can `getDocs(collection('accessCodes'))` and harvest **every**
   run's `{ownerUid, gameId, runId}`. That is exactly the input the IDOR calls and the staff-PIN
   brute-force need. **Fix:** `allow get: if isAuthenticated(); allow list: if false;` (server-side
   `get`-by-id in `getJoinInfo`/`getPublicLeaderboard` is unaffected).

3. **Staff-PIN brute-force + weak RNG (P0/P1, row 40).** `staffSignIn` matches a 6-digit PIN with no
   attempt cap, lockout, or rate limit; combined with (2) a staff token (score-adjust, photo review,
   announcements) is brute-forceable. PINs and access codes use `Math.random()`. **Fix:** per-(run,
   caller) attempt cap + cooldown; generate PIN/codes with `crypto.randomInt`. Folds into rate-limiting
   ([#19](#functional-gaps-new-capabilities)).

4. **Orphaned validation layer + unvalidated `photoUrl` (P0/P1, row 41).** `packages/shared/src/validation.ts`
   (hardened, bilingual, size-capping) is imported by **no** v2 callable — the live callables use
   ad-hoc `!x?.trim()` checks, so there are **no payload-size caps** on `displayName`, `registrationData`,
   `memberNames`, `message`, or `photoUrl`, and `photoUrl` is an arbitrary client string stored on the
   team doc (not constrained to the team's own Storage path). **Fix:** wire the validators into every
   callable; add `requireStorageUrl(url, runId, uid)`; correct the module's stale v1 header.

5. **Answer `attemptLimit` not enforced (P1, row 42).** `Task.smart.attemptLimit` is exposed to the
   client by the sanitizer but **never checked** in `submitTaskAnswer` — quiz/numeric answers are
   server-side brute-forceable. **Fix:** persist `taskAttempts[taskId]` in the scoring transaction;
   refuse past the limit.

6. **`launchRun` not atomic end-to-end (P1, row 43).** The billing transaction consumes a credit, then
   a **separate** `batch.commit` writes the run + access code. A failure between them burns a paid
   credit with no run. **Fix:** fold the run + accessCode writes into the billing transaction so a
   failure rolls back the charge (`playCount` stays best-effort outside).

7. **Referral farming + Pro-expiry (P2, row 44).** `claimReferral` lets N throwaway accounts each refer
   one main account (unbounded free-run farming; only friction is N emails). `launchRun` checks
   `plan === 'pro'` but ignores `proExpiresAt` (relies solely on the deletion webhook). **Fix:** a
   per-referrer velocity/cap (App-Check-gated, [#27](#260--security--storage-rules-verification-suite--shipped)); check `proExpiresAt > now` at launch.

> **Storage PII note (relates to [§26.4](#264--minors--guardian-consent)):** `storage.rules` lets any
> authenticated user read any team's uploaded photos (minors' faces). The 90-day prune ([§15](#15-account-management--privacy))
> bounds retention, but tighter read-scoping (owner/staff/own-team only) should land with the minors gate.

**Surfaces:** `functions/src/index.ts` (station callables, staffSignIn), `functions/src/runs/index.ts`
(launchRun, submitTaskAnswer), `functions/src/payments/index.ts` (claimReferral, launch Pro check),
`firestore.rules` (accessCodes get/list), `packages/shared/src/validation.ts` (wiring),
`scripts/test-rules.mjs` + `scripts/e2e-verify.mjs` (proof). No UI changes.

## Appendix A — Strict AI Coding Rules

These are **mandatory** for any AI (or human) writing RushPoint code. They encode the conventions in
[§23](#23-conventions--footguns) plus the architectural decisions behind the v2.1 updates. Treat a
violation as a failing review.

**Process**
1. **Spec-driven, always.** Non-trivial work goes through OpenSpec: `/opsx:propose` →
   `/opsx:apply` → `/opsx:archive`. No ad-hoc feature coding. Trivial one-liners (typo, copy, an
   obvious fix with existing coverage) may skip the ceremony.
2. **TDD, always.** The first implementation step is a **failing test** that encodes the new behavior;
   confirm it fails for the right reason; write the minimum code to pass; then refactor. Pure logic →
   vitest / `scripts/test-*.ts`; callable behavior → `scripts/e2e-verify.mjs`.
3. **Gates are non-negotiable.** `typecheck`, `npm test`, `lint`, `creator:build`, `e2e` must all be
   green before a change is "done". Never declare done on red.
4. **The code is the source of truth.** Read the actual implementation before changing it; keep
   TECH_SPEC.md in sync when behavior changes.

**Data & backend**
5. **Server-write-only state.** Never write run/team/score/leaderboard/wallet from a client. A
   mutation = a callable in `functions/src/<domain>/index.ts` + re-export + a typed wrapper in
   `services/calls.ts`.
6. **Always use `FIRESTORE_PATHS`.** Never hardcode a Firestore path string.
7. **No growing arrays on a parent document.** Unbounded sequences (per-task progress, logs) go in a
   **subcollection** (1 MB limit + write contention). New code targets the `taskStates` subcollection,
   not a `stages` array. (§4.C)
8. **No ephemeral high-frequency data in Firestore.** Live GPS / presence belongs in **RTDB**
   (bandwidth-billed), never Firestore (per-write-billed). (§4.B)
9. **Never dotted-update an array element** (`stages.0.tasks.1`) — it coerces the array to a map and
   corrupts the run. Rewrite the full object, or (preferred) use the subcollection.
10. **`.set({merge})` + dotted keys writes a literal `"a.b"` field**, not a nested path. Use a real
    nested object.
11. **No compound queries** needing custom indexes — filter/sort in memory.

**Security**
12. **Never trust client-asserted location or completion.** The server re-validates geofence distance
    **and** transit velocity; impossible movement is flagged, not silently accepted. (§7.A)
13. **Answer keys are server-secret.** `secretCode`, `hint` text, quiz `answers`, `numericAnswer`,
    `steps[].answer`, and `visionPrompt` are stripped by `sanitizeTaskForParticipant` and must never
    reach a client payload.
14. **Secrets stay server-side.** Stripe and Gemini keys live in `functions/.env` / Firebase secrets;
    third-party API calls (Gemini Vision) happen only inside Cloud Functions. No secret in any
    `VITE_*` var or client bundle.
15. **Idempotency + transactions** for anything that bills, consumes a credit, or can be double-fired
    (launch, join capacity, hint charge, Stripe webhook). Guard with a transaction and a processed flag.

**Frontend / UX**
16. **Static Tailwind classes only** — no `bg-${x}`. Dynamic per-game color uses inline `style` with
    `branding.primaryColor`.
17. **RTL-correct.** User content uses `dir="auto"`; prefer logical classes (`ms-`, `text-start`).
    creator-web is Hebrew-default; keep both EN + HE strings for ops content.
18. **Keep heavy deps lazy.** MapLibre stays behind `React.lazy`; Battery-Saver mode must fully
    **unmount** it, not just hide it. (§19.B, §21)
19. **Respect accessibility.** Game-juice motion (confetti, banners) honors `prefers-reduced-motion`.
20. **Minimal, scoped diffs.** Match surrounding style; one OpenSpec task ≈ one red-green cycle; don't
    refactor unrelated code in a feature change.
